## 1. 요청부터 결과가 보일 때까지의 흐름

### 1-A. 사용자가 화면을 볼 때 (매 방문)

```
① 사용자가 주소 입력
      │
② GitHub Pages CDN(전 세계 복사본 서버)이 index.html·JS·CSS 전달        ← dist/
      │
③ 브라우저가 필요한 JSON만 따로 받음
      │   matches-2026.json(일정·결과), current-season.json(순위·선수),       ← src/matchData.ts 42행
      │   match/{경기ID}.json(경기 리포트를 열 때만)                          ← src/matchData.ts 58행
      │
④ 브라우저 안에서 계산(순위 정렬, 포아송 승무패 확률, 팀 추천 점수)        ← src/matchData.ts, src/data.ts
      │
⑤ 화면 표시 (서버 계산 0초)
```

### 1-B. 로그인한 사용자가 글·예측·응원팀을 저장할 때

```
① 이메일 입력 → Supabase Auth가 로그인 링크 메일 발송                     ← src/accountApi.ts 31행
② 메일 링크 클릭 → 사이트로 돌아오며 로그인 상태 저장(브라우저)            ← src/accountApi.ts 19~20행
③ 저장 버튼 → 브라우저가 Supabase DB에 직접 insert/upsert                 ← src/accountApi.ts 47·65·85행
④ DB의 RLS 규칙이 "본인 것만", "경기 시작 전만", "1분 5개까지" 검사          ← supabase/schema.sql
⑤ 성공하면 목록 다시 읽어 화면 갱신                                        ← src/Account.tsx 111행
```

### 1-C. 매일 자료 갱신 (예약 작업)

```
① 06:00 KST GitHub Actions가 임시 컴퓨터(ubuntu-latest) 1대 준비           ← deploy.yml
② npm install
③ fetch-matches.mjs: 1~12월 × 리그 2개 = 일정 요청 24회
④ 새로 끝난 경기만 경기당 상세 요청 4개 (동시 3경기, 실패 시 3번까지 재시도)  ← fetch-matches.mjs 23·30~47·86~127행
⑤ public/data/matches-2026.json, match/*.json 저장 (임시 디스크)
⑥ vite build → dist/
⑦ GitHub Pages에 배포 → 몇 분 안에 새 자료가 보임
   (③~④가 실패해도 저장소에 있던 자료로 ⑥⑦은 계속 진행 = continue-on-error)
```

## 2. 웹 요청 안에서 처리할 일 vs Queue/Worker로 분리할 일

Queue(작업 대기열: 할 일 목록을 줄 세워 두는 곳)와 Worker(대기열에서 일을 꺼내 처리하는 별도 컴퓨터)는 **지금 필요 없습니다.** 사용자가 기다리는 무거운 작업이 없기 때문입니다.

| 일 | 걸리는 시간 | 처리 위치 | 판단 | 근거 파일 |
|---|---|---|---|---|
| 화면·JSON 전달 | 즉시 (CDN) | 웹 요청 안 | ✅ 그대로 | `dist/` |
| 순위·확률·팀 추천 계산 | 미확인 (체감상 즉시) | 브라우저 안 | ✅ 그대로 | `src/matchData.ts`, `src/data.ts` |
| 로그인 메일 발송 | 수 초 (Supabase가 처리) | Supabase 내부 | ✅ 그대로 | `src/accountApi.ts` 31행 |
| 응원 글·예측·응원팀 저장 | 1건 수백 ms 이하 (추정) | 웹 요청 안 (Supabase) | ✅ 그대로 | `src/accountApi.ts` |
| 경기 자료 수집 | **중앙값 8.8초, 최대 9.3초** (측정, 평소 모드) | **예약 작업** (GitHub Actions) | ✅ 이미 분리됨 — 사실상 "하루 1번 도는 Worker" | `scripts/fetch-matches.mjs` |
| 전체 재수집 `--refresh` | 미확인 (경기 466개 × 요청 4개) | 예약 작업 / 수동 | ✅ 사용자 요청과 무관 | `scripts/fetch-matches.mjs` 22행 |
| 사이트 빌드 | **중앙값 10.5초, 최대 21.1초** (측정) | 예약 작업 | ✅ 이미 분리됨 | `deploy.yml` |
| (미래) 영상 업로드·분석 | — | **Queue + Worker 필수** | 기능 추가 시에만 | 해당 코드 없음 |

**규칙(앞으로 기능을 추가할 때)**: 사용자가 버튼을 누르고 **10초 넘게** 기다려야 하거나, 메모리를 **1GB 넘게** 쓰거나, 외부 유료 API를 여러 번 부르는 일은 웹 요청에서 빼서 Queue/Worker로 보냅니다.

## 4. 배포 구조 비교와 추천

| 구조 | 이 프로젝트에 적용하면 | 장점 | 단점 | 월 고정비 |
|---|---|---|---|---|
| ① 단일 서버 (VPS: 빌려 쓰는 가상 컴퓨터 1대에 웹·DB·예약 작업 모두) | Nginx + Postgres + cron을 직접 설치 | 모든 걸 마음대로 설정, 요금 예측 쉬움 | 보안 업데이트·백업·장애 대응을 직접 해야 함. 서버 1대가 죽으면 전부 멈춤 | 유료 (업체별 상이, 미확인) |
| **② 관리형 서비스 (현재 구성)** | GitHub Pages(화면) + GitHub Actions(예약 작업) + Supabase(로그인·DB) | 서버 관리 0, 무료, 이미 동작 중, CDN이라 접속 몰려도 버팀 | 무료 요금제 제한(Supabase 7일 미사용 일시정지, Pages 상업 이용 제한) | **0원** |
| ③ 웹/API + 분석 Worker 분리 | ② + 별도 API 서버 + Queue + Worker | 무거운 작업이 화면을 느리게 하지 않음, GPU 확장 쉬움 | 지금은 무거운 작업이 없어 **만들 이유가 없음** | Worker 서비스 비용 추가 |

### 추천: ② 관리형 서비스 (현재 구성 유지)

- 측정 결과 가장 큰 작업이 하루 1번, 10초 안팎, 메모리 0.5GB 미만입니다 (3장).
- 사용자 요청은 전부 CDN과 Supabase가 처리하므로 우리가 관리할 서버가 필요 없습니다 (1장).
- 이미 GitHub Actions가 "하루 1번 도는 Worker" 역할을 하고 있어서 ③의 장점을 비용 없이 얻고 있습니다.
- **③으로 옮길 조건**: 사용자가 파일을 올리거나, 1건에 10초 넘는 계산을 사용자가 요청하는 기능이 생길 때. 그때도 화면·Supabase는 그대로 두고 **Worker 하나만 추가**합니다.

## 5. 비용 계산식

가격 출처(확인일 2026-11-21): [Supabase 가격](https://supabase.com/pricing), [Supabase 과금 안내](https://supabase.com/docs/guides/platform/billing-on-supabase), [GitHub Pages 한도](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

### 월 고정비

```
월 고정비 = GitHub Pages + GitHub Actions + Supabase 요금제 (+ 도메인)
         = 0원       + 0원 (공개 저장소) + 0원 (Free) 또는 25달러 (Pro)
```

| 항목 | 지금 | 바뀌는 조건 |
|---|---|---|
| GitHub Pages | 0원 | 요금제 없음. 월 100GB 넘으면 Cloudflare Pages로 이전 |
| GitHub Actions | 0원 | 저장소를 비공개로 바꾸면 무료 2,000분/월 이후 과금 (분당 단가 미확인 → [GitHub 요금](https://docs.github.com/en/billing) 확인) |
| Supabase | 0원 | 7일 미사용 일시정지가 곤란하거나 DB 500MB·MAU 5만 초과 시 Pro **월 25달러부터** |
| 자체 도메인 (선택) | 0원 | 사면 연 수만 원 (업체별 상이, 미확인) |

### 작업 1회당 변동비

```
자료 수집 1회 비용 = Actions 사용 분 × 분당 단가 + 외부 API 비용
                 = 약 2~3분(추정) × 0원(공개 저장소) + 0원(kleague.com 무료)
                 = 0원

방문 1회 비용     = 전송량 × 전송 단가 + Supabase 요청 비용
                 = 약 2.5MB(추정) × 0원(Pages 무료 한도 안) + 0원(Free 한도 안)
                 = 0원 (월 약 4만 방문까지)
```

### 무료 한도를 넘었을 때의 계산식 (숫자는 측정 후 대입)

```
Pages 한도 도달 방문 수  = 100GB ÷ 방문 1회 전송량(측정 필요, 현재 추정 2.5MB) ≈ 약 40,000회/월
Supabase Pro 월 비용     = 25달러 + max(0, MAU − 100,000) × 0.00325달러 + 디스크 초과 GB × 0.125달러
                          + 전송량 초과분 × 단가(미확인 → Supabase 가격 페이지 확인)
```

- MAU(월 활성 사용자: 한 달에 한 번 이상 로그인한 사람 수)는 Supabase → **Reports → Auth**에서 확인
- 방문 1회 전송량은 3장의 "Network 탭" 방법으로 측정해 위 식에 대입

## 6. 작업 상태와 실패 처리

이 프로젝트에서 "작업"은 **매일 예약 작업 1회**와 그 안의 **경기별 상세 기록 받기**입니다. 사용자 요청에는 대기열 상태가 없습니다(즉시 성공/실패).

### 상태 정의

| 상태 | 예약 작업 전체 (GitHub Actions 실행) | 경기별 상세 기록 | 확인 위치 | 근거 |
|---|---|---|---|---|
| **queued** (대기) | Actions가 실행을 예약하고 임시 컴퓨터를 기다리는 중 | 종료됐는데 `match/{ID}.json`이 없는 경기 = 받을 목록(`todo`) | Actions 탭 노란 점 / 로그 "상세 기록 새로 받기 N개" | `fetch-matches.mjs` 83~84행 |
| **processing** (처리 중) | 설치·수집·빌드·배포 단계 진행 중 | `pool()`이 동시 3개씩 요청 중 | Actions 탭 노란 회전 아이콘 | `fetch-matches.mjs` 48~54행 |
| **completed** (완료) | 배포까지 성공 (초록 체크) | 상세 파일 저장 완료 | Actions 탭 초록 체크 / 로그 "저장 완료" | `fetch-matches.mjs` 120·175행 |
| **failed** (실패) | 빌드·배포 실패 (빨간 X) | 3번 재시도 후에도 실패 → `failed` 목록에 기록 | Actions 로그 "상세 기록 실패 N개" | `fetch-matches.mjs` 124~126·176행 |

### 재시도

| 단계 | 현재 방식 | 근거 | 보완 제안 |
|---|---|---|---|
| 요청 1개 | 실패 시 0.8초 → 1.6초 기다리며 최대 3번 | `fetch-matches.mjs` 30~47행 | 충분함 |
| 경기 1개 | 이번에 실패하면 다음날 실행 때 자동으로 다시 받음 (파일이 없으면 `todo`에 다시 들어감) | `fetch-matches.mjs` 83행 | 같은 경기가 **3일 연속** 실패하면 알림(이슈 생성) 추가 |
| 수집 전체 | 실패해도 기존 자료로 배포 계속 (`continue-on-error`) | `deploy.yml` | 실패 시 이메일 알림 켜기(7장) |
| 빌드·배포 | 실패하면 그날은 이전 사이트가 그대로 유지됨 | `deploy.yml` | 수동 재실행: Actions → **Run workflow** |

### 중복 실행 방지

| 위험 | 현재 방지 장치 | 근거 |
|---|---|---|
| 예약 실행과 push 실행이 겹침 | `concurrency: group: pages, cancel-in-progress: true` → 새 실행이 오면 이전 실행 취소, 동시에 1개만 | `deploy.yml` |
| 같은 경기를 두 번 받음 | 상세 파일이 이미 있으면 건너뜀 / 같은 경기 ID 중복 제거(`seen`) | `fetch-matches.mjs` 73~74·83행 |
| 같은 사람이 같은 경기에 예측 2번 | 기본 키 `(user_id, match_id)` + `upsert` → 덮어쓰기 | `schema.sql`, `accountApi.ts` 65행 |
| 응원팀 중복 저장 | 기본 키 `(user_id, kind, item_id)` | `schema.sql` |
| 응원 글 버튼 두 번 클릭 | 보내는 동안 버튼 비활성(`busy`) + 1분 5개 제한 트리거 | `Account.tsx` 111·120행, `schema.sql` |

### ⚠️ 발견한 약점: 수집 자료가 저장되지 않음

예약 작업이 받은 새 자료는 Actions 임시 컴퓨터의 디스크(`writeFileSync`)에만 쓰이고 저장소에 커밋되지 않습니다. 그래서 **매일 같은 경기를 다시 받고**, 공식 사이트에서 자료가 사라지거나 막히면 그동안 받은 자료도 함께 사라집니다. 저장소에 있는 자료는 마지막으로 직접 커밋한 날의 것뿐입니다.

**고치는 법**: `deploy.yml`의 수집 단계 뒤에 "`public/data`에 바뀐 게 있으면 커밋·push" 단계를 넣고, `permissions`에 `contents: write`를 줍니다. 이렇게 하면 "60일 동안 커밋이 없으면 예약 실행이 꺼지는" GitHub 규칙도 함께 피할 수 있습니다.
