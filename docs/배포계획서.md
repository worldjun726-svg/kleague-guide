## 1. 구조와 배포 역할

이 사이트는 **“미리 만들어 둔 파일을 나눠 주는 사이트”** 입니다. 사용자가 접속할 때마다 계산하는 우리 서버가 없습니다. 무거운 작업은 하루 한 번 자동으로 공식 홈페이지에서 경기 자료를 받아 JSON 파일(데이터를 담은 텍스트 파일)로 저장하는 일뿐입니다.

```
[매일 06:00 KST] GitHub Actions
   └─ scripts/fetch-matches.mjs → kleague.com에서 일정·결과·경기기록 받기
   └─ vite build → dist/ (HTML·JS·CSS·JSON·영상)
   └─ GitHub Pages에 올리기
                      ↓
[사용자 브라우저] ── 화면·JSON 파일 읽기 ──→ GitHub Pages
          └──── 로그인·응원팀·예측·응원 글 ──→ Supabase (Auth + Postgres DB, 행 단위 보안 규칙)
```

| 역할 | 해당 | 판단 근거 파일 | 쉬운 설명 |
|---|---|---|---|
| A 정적 화면 | ✅ | `package.json`(React 19 + Vite), `vite.config.ts`(`base: './'`), `index.html`, `.github/workflows/deploy.yml` | 빌드하면 `dist/` 폴더(4.7MB, 파일 475개)가 나오고 이것만 올리면 됩니다. 주소 이동은 `#/team/seoul`처럼 `#` 방식이라 서버 설정이 필요 없습니다. |
| B 웹앱/API | ❌ (BaaS로 대체) | `src/accountApi.ts`, `src/supabaseConfig.ts`, `supabase/schema.sql` | 직접 만든 API 서버가 없습니다. 브라우저가 Supabase에 바로 요청하고, DB의 RLS(행 단위 보안: “내 글만 지우기” 같은 규칙)가 권한을 지킵니다. |
| C 상시 연결 | ❌ | `src/liveData.ts`, `src/Live.tsx` | 웹소켓·Supabase Realtime 사용 없음. 라이브 화면은 `live-sample.json`(임의 샘플)을 한 번 읽습니다. |
| D 예약 작업 | ✅ | `.github/workflows/deploy.yml`(`cron: '0 21 * * *'`), `scripts/fetch-matches.mjs` | 매일 자료를 새로 받고 사이트를 다시 만듭니다. 실패해도 저장소에 있는 자료로 배포를 계속합니다(`continue-on-error`). |
| E 데이터·데모 화면 | ✅ | `public/data/*.json`, `public/data/match/*.json`(465개), `public/data/sample-data.json`, `scripts/generate_demo.py` | 순위·경기 기록은 실제 공식 자료, 라이브·2025 예시는 합성 데이터입니다. 화면에 “예시”라고 표시됩니다. |
| F 비동기 분석 | ❌ | — | 영상 분석·OpenCV·FFmpeg·YOLO·PyTorch·GPU 사용 없음. `public/media/hero.mp4`(2.1MB)는 첫 화면 배경 영상일 뿐 사용자가 올리지 않습니다. 업로드 기능·객체 저장소(파일 보관 전용 서비스)도 필요 없습니다. |

> 오래 걸리는 분석 작업이 없으므로 `화면 → API 접수 → 객체 저장소/작업 대기열 → Worker → DB` 구조는 **지금 필요하지 않습니다.** 나중에 “사용자가 경기 영상을 올려 분석” 같은 기능이 생기면 그때 8장 확장 순서를 따릅니다.

## 3. 분석 1회 자원 대시보드

이 프로젝트의 “핵심 작업 1회”는 사용자 요청마다 도는 분석이 아니라 **매일 1회 도는 자료 수집 + 빌드**입니다. 사용자가 늘어도 이 작업 횟수는 늘지 않습니다. 사용자 수에 따라 늘어나는 것은 **파일 전송량**과 **Supabase 요청량**입니다.

- **대표 작업 ①** 자료 수집 `node scripts/fetch-matches.mjs` (평소 모드: 새로 끝난 경기만 받기). 입력: 기존 `public/data` 1.87MB, 경기 500개(종료 466개, 상세 기록 465개 보유)
- **대표 작업 ②** 사이트 빌드 `node node_modules/vite/bin/vite.js build` (= `npm run build:bundle`). 입력: 모듈 1,651개
- **측정 환경**: Windows 11 Pro, 논리 CPU 8개, Node.js v24.22.1, 가정용 인터넷. 자료 수집은 저장소를 건드리지 않도록 `test-results/measure` 복사본에서 실행 후 삭제
- **측정 방법**: PowerShell로 프로세스를 띄워 50ms마다 최대 메모리(PeakWorkingSet)를 읽음. 준비 실행 1회는 버리고 3회 기록
- **측정 날짜**: 2026-11-21

| 동시 사용자 | 우리 서버 CPU/GPU | 메모리 | 예상 대기시간 | 근거 |
|---|---|---|---|---|
| 1명 | 0 (관리형) | 0 | 첫 화면 약 1~3초 (추정) | 첫 방문 전송량 ≈ JS 178KB(gzip 측정) + CSS 19KB + 배경 영상 2.1MB + 포스터 0.13MB + 경기 목록 JSON 약 0.1MB(압축 추정) ≈ **2.5MB** |

### 월 사용량별 비용

여기서 “회”는 **사이트 방문(첫 화면 로딩) 수**로 봅니다. 가정: 방문 1회 = 2.5MB 전송, 방문자의 10%가 로그인해 DB 요청 20회.

| 월 방문 | 서버 (Actions) | 화면 전송 (Pages) | DB/저장소 (Supabase) | 합계 |
|---|---|---|---|---|
| 100회 | 0원 — 하루 1회 × 약 3분 × 30일 ≈ 90분 (추정, 공개 저장소는 무료) | 100 × 2.5MB = **0.25GB** / 한도 100GB | 로그인 약 10명 / 한도 MAU 5만 | **0원** |
| 1,000회 | 0원 | **2.5GB** | 약 100명, DB 수 MB | **0원** |
| 10,000회 | 0원 | **25GB** | 약 1,000명, DB 수십 MB | **0원** |

- 무료 한도 초과 지점(추정): Pages 월 100GB ÷ 2.5MB ≈ **월 방문 약 4만 회**. 배경 영상(2.1MB)이 전송량의 80% 이상이므로 영상을 줄이면 한도가 크게 늘어납니다.
- Supabase: DB 500MB, 월 활성 사용자 5만 명까지 무료. 응원 글 1개 ≈ 0.5KB 가정 시 100만 개 ≈ 0.5GB (추정).
- 모든 사용자 수 관련 값은 **선형 추정**입니다(동시 접속 부하 시험은 하지 않음).

**초보자용 결론 3줄**
1. **최소 사양**: 서버를 따로 빌릴 필요 없음. GitHub 무료 + Supabase 무료로 0원.
2. **쾌적 사양**: 월 방문 4만 회를 넘거나 상업 서비스로 바꾸면 화면을 Cloudflare Pages로 옮기고 Supabase Pro(월 25달러)로 올림.
3. **병목**: 계산 능력이 아니라 ① 배경 영상 전송량, ② Supabase 무료 요금제의 **7일 미사용 시 일시정지**, ③ 무료 메일 발송 시간당 제한(로그인 메일).

**지금 시작할 최소 비용 CPU안**: 현재 구성 그대로(GitHub Actions 무료 러너가 CPU 작업 전부 담당).
**GPU로 옮길 조건**: 이 프로젝트에는 GPU 작업이 없습니다. 앞으로 “경기 영상에서 선수 위치 추적(YOLO 등)”처럼 영상 1개 분석에 CPU로 1분 이상 걸리는 기능을 추가할 때만 검토합니다. 그때 옮길 부분은 **새로 만드는 분석 Worker 하나뿐**이고, 화면·Supabase는 그대로 둡니다.

## 6. 환경변수

현재 이 프로젝트는 환경변수(배포 설정에 따로 넣는 비밀/설정 값)를 쓰지 않고, 공개해도 되는 값을 코드 파일에 직접 적습니다.

| 이름 | 용도 | 현재 파일 | 배포 설정 위치 |
|---|---|---|---|
| `SUPABASE_URL` | Supabase 프로젝트 주소 (공개 값) | `src/supabaseConfig.ts` (상수로 기록됨, 미커밋 수정 상태) | 지금처럼 코드에 두어도 됨. 원하면 `VITE_SUPABASE_URL`로 옮겨 GitHub → Settings → Secrets and variables → Actions → **Variables** |
| `SUPABASE_ANON_KEY` | 브라우저용 공개 키 (`sb_publishable_…` 형식 확인) | `src/supabaseConfig.ts` | 위와 같음 (`VITE_SUPABASE_ANON_KEY`) |
| (사용 금지) service_role / `sb_secret_…` 키 | 모든 보안 규칙을 무시하는 관리자 키 | 코드에 없음 ✅ | **절대 브라우저 코드·저장소에 넣지 않음.** 필요해지면 서버 쪽(Actions Secrets)에만 |
| `config/secret_key`, `config/field_encryption_key` | 어떤 코드도 읽지 않음 (사용처 검색 결과 0건) | `config/` (저장소에 커밋됨) | **저장소에서 삭제** (7장) |

✅ 브라우저에 노출된 키는 공개용 publishable 키뿐이라 정상입니다. 데이터 보호는 `supabase/schema.sql`의 RLS 규칙이 맡습니다.
✅ 영구 저장이 로컬 디스크에 의존하지 않습니다. 사용자 데이터는 Supabase, 경기 자료는 git 저장소와 매일 수집에 있습니다. (`localStorage`는 팀 추천 답변 기억용 편의 기능뿐)

## 8. 배포 순서

1. **보안 정리 먼저**: `config/` 키 파일 2개와 `codex.toml` 내용을 확인 → 쓰이는 키라면 폐기·재발급 → 저장소에서 제거하고 `.gitignore`에 추가해 커밋.
2. **Supabase 확인**: 대시보드에서 `schema.sql` 최신본 실행, Authentication → URL Configuration에 Pages 주소 등록 확인.
3. **미커밋 수정 3개 정리**: `src/supabaseConfig.ts`(공개 키만 들어 있는지 다시 확인), `supabase/schema.sql`, 메모 파일을 커밋.
4. **push** → GitHub Actions의 “Deploy to GitHub Pages”가 초록색으로 끝나는지 확인.
5. **배포 주소에서 10장 체크리스트** 실행.
6. (권장) 자료 수집 후 `public/data`를 커밋하는 단계와 `fetch-matches.mjs` 경로 수정 추가.
7. **확장 조건이 오면**: 상업화하거나 월 방문 4만 회 초과 → Cloudflare Pages로 화면 이전 / 비시즌에도 로그인 기능을 계속 켜 둬야 함 → Supabase Pro / 로그인 메일 실패 증가 → Resend SMTP 연결.
8. **(먼 미래) 영상 분석 기능을 추가할 때만**: Supabase Storage에 직접 업로드(서명된 업로드 주소) → 작업 표(job 테이블)에 접수 → 별도 CPU Worker(예: Render·Railway·Fly.io Worker) → 결과 DB 저장. CPU로 1건에 1분 이상 걸리면 그 Worker만 GPU 서비스(Modal·RunPod 등)로 옮김. 도입 시점에 다시 1회 자원 측정.

## 9. 문제 대비표

| 예상 문제 | 확인 위치 | 대처 |
|---|---|---|
| 사이트가 옛날 자료 그대로 | GitHub → Actions → 최근 실행의 `fetch-matches` 단계 로그 | 공식 사이트 오류면 다음날 자동 재시도. 계속 실패하면 응답 구조가 바뀐 것 → 스크립트 수정 |
| 매일 자동 배포가 멈춤 | Actions 탭에 “scheduled workflow disabled” 안내 | 60일 비활성 때문. Actions에서 다시 Enable, 또는 7장의 자료 자동 커밋 적용 |
| 로그인 메일이 안 옴 | Supabase → Authentication → Logs | 무료 발송 한도 초과 → 잠시 후 재시도, 사용자 많으면 Resend SMTP 연결 |
| 로그인 링크 누르면 다른 주소로 감 | Supabase → Authentication → URL Configuration | Site URL·Redirect URLs에 실제 Pages 주소 추가 |
| 로그인·응원 글이 전부 실패 | Supabase 대시보드에 “Paused” 표시 | 7일 미사용 일시정지 → Restore. 자주 생기면 Pro 전환 |
| 화면 빈 페이지·JSON 못 읽음 | 브라우저 개발자도구(F12) → Network | 경로 문제면 `vite.config.ts`의 `base: './'` 유지 확인 |
| 빌드 실패 | Actions → `npm run build:bundle` 로그 | 로컬에서 같은 명령 실행해 오류 재현 |
| 전송량 경고 메일 | GitHub에서 오는 Pages 사용량 메일 | 배경 영상 경량화 → 그래도 넘으면 Cloudflare Pages 이전 |
| 응원 글 도배·악성 글 | Supabase → Table Editor → `comments` | `hidden`을 `true`로. 1분 5개 제한 트리거는 이미 있음 |
